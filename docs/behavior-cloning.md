# Benchmark 1: pushing-only behavior cloning

The implementation passes 28 tests and a short simulator preflight. The first trained policy achieves **7/9 validation successes**; see [the validation report](bc-validation.md) for metrics, failures, checkpoint and videos.

## What the network learns

Each selected teacher step supplies **state before action → issued action**. Inputs are eight numbers: end-effector minus cube X/Y, goal minus cube X/Y, and sine/cosine of cube and grip-site headings. Quaternion order is explicitly converted: MuJoCo cube WXYZ, SciPy grip site XYZW. Positions use robot world axes; original phone orientation is preserved.

The MLP has 8 inputs, two 64-unit ReLU layers and two outputs. Outputs are `0.2 * tanh(...)`: normalized world-frame OSC X/Y commands, **not absolute end-effector coordinates or joint angles**. The OSC controller converts Cartesian control into robot joint torques. No future human position, recorded time, episode identifier, or next simulator state enters the network.

The loader selects `human_push`, `goal_dwell` and `reference_hold` from successful recorded-object-feedback teacher rollouts. This gives 3,318 training pairs from 37 episodes. Six successful validation references give 423 pairs for validation action loss. Failed replays remain documented but are excluded from expert labels. Samples from one recording never cross splits. Only training position features determine normalization; heading sine/cosine remain unscaled.

Human recordings provide the object-motion references used by the scripted retargeting teacher. The robot action labels are generated by running that teacher in simulation. These are **derived robot rollouts**, not direct robot demonstrations. This first benchmark uses privileged simulator cube pose and a known goal; it is a state-based policy, not a vision-language model.

## Commands

Run from the repository root. Install the optional CPU learning dependencies with the lockfile:

```bash
uv sync --locked --extra learning --group dev
source .venv/bin/activate
push-bc-prepare
# Run only when ready to start actual training:
push-bc-train --epochs 200
push-bc-evaluate --checkpoint outputs/bc_training/best.pt
```

If using pip instead of uv, first follow the base environment instructions, then install `torch==2.5.1` from `https://download.pytorch.org/whl/cpu` and reinstall the project editable. CPU PyTorch is enough for this network; system CUDA is unchanged. Dataset preparation requires the retained local NPZ rollouts. On a fresh checkout, regenerate training and validation rollouts using the documented batch commands; raw recordings are not required for replay of the published numeric tracks.

Use a new `--output` directory for each training/evaluation experiment; existing checkpoints and evaluation results are protected from accidental overwrite.

For a fresh checkout, regenerate the rollout files expected by the dataset index first (these commands use the committed numeric samples):

```bash
MUJOCO_GL=egl python scripts/run_batch.py \
  --manifest data/manifests/human_object_teacher.json \
  --push-controller human-object-feedback --no-video --success-videos 0 \
  --output outputs/human_object_teacher
MUJOCO_GL=egl python scripts/run_batch.py \
  --manifest data/manifests/public_training_batch_04.json \
  --push-controller human-object-feedback --no-video \
  --output outputs/training_batch_04
MUJOCO_GL=egl python scripts/run_batch.py \
  --manifest data/manifests/public_validation_batch_01.json \
  --push-controller human-object-feedback --no-video \
  --output outputs/validation_batch_01
push-bc-prepare
```

The combined teacher manifest includes all 42 sources; the index uses its first 32 outputs plus the consistently named batch-04 outputs for the last ten.

Preparation writes `outputs/bc_dataset/dataset.npz` and `provenance.json`, including source hashes and exact sample counts. Training uses Adam, learning rate 0.001, batch size 128, seed 7, up to 200 epochs, normalized action MSE and finite-gradient checks. `best.pt` is selected by **validation action loss**, not claimed to be the best task performer. `last.pt` and per-epoch losses are also saved. Evaluate candidate checkpoints on validation only if selecting by task success; document all comparisons.

## Closed-loop evaluation

Evaluate all nine validation starts, including teacher failures. Initialization and independent goal geometry come from saved initial-state metadata and calibration. The evaluator never opens raw videos or loads recorded future trajectories. A shared feature function ensures runtime inputs match training inputs.

Approach, lowering, fixed 0.868 m grip-site height, initial goal-facing paddle yaw, containment dwell and withdrawal remain scripted. Only pushing X/Y comes from the network. The approach uses initial cube/goal geometry and 12 mm clearance. Upon containment, the controller holds the achieved position for 0.2 s. A push stops at successful dwell or 10 s, whichever comes first; approach/withdrawal time is excluded. Final containment after withdrawal and the same finite-state, lift, table and pre-push disturbance checks as teacher replay determine success.

`outputs/bc_validation/` stores each policy rollout, metrics and a summary with checkpoint hash, success count and final target distances. Up to three successful videos are rendered and retained automatically. Failed videos are removed; numerical failure evidence remains. This benchmark does not train approach or withdrawal; those are planned for benchmark 2.

The test recordings stayed unopened until architecture, checkpoint selection and evaluation protocol were frozen. The completed opening-only test evaluation achieves **8/9 successes**. Final test evaluation now requires an explicit test split and frozen protocol; see [the test report](bc-test.md). Validation action loss measures label matching; actual success must be measured in the simulator. A small state-only MLP may drift away from demonstrated states or struggle with contact; no generalization result is assumed.

## Verification before training

On 11 October 2026, all 28 tests passed. Dataset preparation was run on the retained real rollouts; counts and hashes are published in [the dataset audit](../data/manifests/bc_dataset_provenance.json). A zero-action, untrained network completed scripted approach/withdrawal and two pushing control steps in simulation. The state remained finite, the cube stayed on the table, approach displacement was below 2 mm, and the 0.1-second diagnostic timeout fired. This is a wiring check, not a learned task result. At this preflight checkpoint, no optimizer had run on the real dataset and no trained checkpoint existed. The subsequent training and validation run is documented in [the validation report](bc-validation.md); test opening scenes were subsequently evaluated under the frozen protocol, yielding 8/9 successes.
